# Kong v1.5 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Convertir Kong de bucle endless de una pantalla en un juego terminable de 5 mapas, con Kong trepando y una pantalla final que acaba en victoria.

**Architecture:** `level.ts` deja de exportar constantes únicas y pasa a exportar un array de 5 `Layout`. Los módulos puros (`player.ts`, `barrels.ts`) **reciben el layout por parámetro** en vez de importarlo — es el cambio estructural del plan y lo que obliga a tocar sus tests. `KongGame.tsx` resuelve el layout una vez por nivel en `rebuildLevel()`, que ya es el punto donde rehornea el backdrop cacheado.

**Tech Stack:** TypeScript estricto, React 19, canvas 2D, vitest.

**Spec:** `specs/27-kong-v15.md`

## Global Constraints

- **Next.js 16.2.6**: leer `node_modules/next/dist/docs/` antes de tocar APIs de Next. Este plan casi no las toca (canvas + lógica pura); la excepción es la play-page.
- **Comentarios y nombres de tests en inglés** (convención del repo). El chat y los specs, en castellano.
- **Ficheros y carpetas en kebab-case**; componentes React en PascalCase.
- **Commits: SOLO Paco.** Cada tarea termina dejando el working tree verificado y el mensaje de commit exacto propuesto. Nunca ejecutar `git commit`.
- **Sin regresiones**: `npm test` (109 tests, 18 ficheros), `npx tsc --noEmit` y `npm run build` deben quedar limpios al final de cada tarea.
- **Nunca arrancar un `next dev`**: Paco tiene el suyo en :3000.
- **No tocar** `player.ts` en su física (gravedad, salto, trepado), martillos ni scoring por barril. Solo su forma de recibir la geometría.

## Task 2: Invariantes de layout — la red de seguridad

**Files:**
- Create: `components/games/kong-logic/level-invariants.ts`
- Test: `components/games/kong-logic/level.test.ts`

**Interfaces:**
- Consumes: `Layout`, `LAYOUTS` (Task 1), `girderYAt`, `brokenLadderSet`
- Produces: `checkLayout(layout: Layout, brokenLadders: number): string[]` — devuelve la lista de problemas; vacía significa layout jugable.

**Esta tarea va antes de dibujar ningún layout nuevo.** Es el riesgo nº1 del spec: hoy el trofeo tiene **7 px de margen** (`dyT = 53,14` contra un límite de 60) y ningún test lo cubre.

- [ ] **Step 1: Escribir los tests que fallan**

```ts
import { checkLayout } from './level-invariants';
import { LAYOUTS, configFor } from './level';

it('reports no problems for every shipped layout', () => {
  LAYOUTS.forEach((layout, i) => {
    const broken = configFor(i + 1)[3];
    expect({ map: i + 1, problems: checkLayout(layout, broken) })
      .toEqual({ map: i + 1, problems: [] });
  });
});

it('detects an unreachable trophy', () => {
  const broken = { ...LAYOUTS[0], trophy: { x: 300, y: -500 } };
  expect(checkLayout(broken, 0)).toContain('trophy unreachable');
});

it('detects a floor with no way up once ladders are broken', () => {
  const oneLadder = {
    ...LAYOUTS[0],
    ladders: LAYOUTS[0].ladders.filter((l) => l.from !== 2 || l.x === 180),
  };
  expect(checkLayout(oneLadder, 3)).toContain('floor 2 has no exit');
});
```

- [ ] **Step 2: Ejecutar y ver fallar**

Run: `npx vitest run components/games/kong-logic/level.test.ts`
Expected: FAIL — `level-invariants` no existe.

- [ ] **Step 3: Implementar los 5 invariantes**

`checkLayout` comprueba, devolviendo un string por problema:

1. `'trophy unreachable'` — recorre la viga superior píxel a píxel; debe existir al menos una `x` donde `|x − trophy.x| < 22` y `−34 < girderYAt(topGirder, x) − trophy.y < 60`. **Son las constantes reales de `KongGame.tsx`** (`TROPHY_REACH_X = 22`): impórtalas o duplícalas con comentario de trazabilidad, no las adivines.
2. `'floor N has no exit'` — para cada viga salvo la superior, debe quedar ≥1 escalera hacia arriba **después de aplicar `brokenLadderSet`** con el número de roturas del mapa.
3. `'kong has no girder'` — `layout.kong.girder` existe y su `x` cae en `[x0, x1]`.
4. `'hammer N off girder'` — cada martillo sobre una viga existente y dentro de su rango.
5. `'spawn invalid'` — el spawn en viga existente y no dentro del alcance del trofeo.

- [ ] **Step 4: Verde**

Run: `npm test`

- [ ] **Step 5: Dejar listo para commit**

Mensaje: `test(kong): add layout playability invariants`
